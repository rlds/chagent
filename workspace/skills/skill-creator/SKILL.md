# 技能创建器

本技能为创建高效的技能提供指导。

## 关于技能

技能是模块化、自包含的软件包，通过提供专门的知识、工作流和工具来扩展 agent 的能力。可以把它们视为面向特定领域或任务的"上手引导"——它们把 agent 从通用型转变为配备程序性知识的专用型 agent，而这些程序性知识是任何模型都无法完全具备的。

### 技能能提供什么

1. 专门的工作流 —— 针对特定领域的多步骤流程
2. 工具集成 —— 使用特定文件格式或 API 的指引
3. 领域专业知识 —— 公司特有的知识、模式定义、业务逻辑
4. 捆绑资源 —— 用于复杂和重复性任务的脚本、参考文档和素材

## 核心原则

### 精简是关键

上下文窗口是一种公共资源。技能与其他一切 agent 所需内容共享上下文窗口：系统提示词、对话历史、其他技能的元数据，以及用户的实际请求。

**默认假设：agent 已经非常聪明。** 只补充 agent 尚不具备的上下文。对每一条信息都要自问："agent 真的需要这个解释吗？"以及"这段文字值得它消耗的 token 吗？"

优先使用简洁的示例，而不是冗长的解释。

### 设定合适的自由度

让具体程度与任务的脆弱性和可变性相匹配：

**高自由度（基于文本的指令）**：适用于多种方案都可行、决策取决于上下文，或用启发式规则引导方案的情况。

**中等自由度（伪代码或带参数的脚本）**：适用于已有首选模式、允许一定变通，或配置会影响行为的情况。

**低自由度（特定脚本、少量参数）**：适用于操作脆弱易错、一致性至关重要，或必须遵循特定顺序的情况。

把 agent 想象成在探索一条路径：旁边是悬崖的窄桥需要明确的护栏（低自由度），而开阔的田野则允许许多走法（高自由度）。

### 技能的结构

每个技能都由必需的 SKILL.md 文件和可选的捆绑资源构成：

```
skill-name/
├── SKILL.md（必需）
│   ├── YAML frontmatter 元数据（必需）
│   │   ├── name:（必需）
│   │   └── description:（必需）
│   └── Markdown 正文指令（必需）
└── 捆绑资源（可选）
    ├── scripts/          - 可执行代码（Python/Bash 等）
    ├── references/       - 按需加载到上下文中的文档
    └── assets/           - 输出中使用的文件（模板、图标、字体等）
```

#### SKILL.md（必需）

每个 SKILL.md 都由以下部分组成：

- **Frontmatter**（YAML）：包含 `name` 和 `description` 字段。这是 agent 用来判断技能何时被使用的唯一字段，因此必须清晰、全面地描述该技能是什么，以及何时应该使用它。
- **正文**（Markdown）：使用该技能的指令和指导。只有在技能被触发后（如果确实触发）才会加载。

#### 捆绑资源（可选）

##### 脚本（`scripts/`）

用于需要确定性可靠性或会被反复重写的任务的可执行代码（Python/Bash 等）。

- **何时包含**：当同一段代码被反复重写，或需要确定性可靠性时
- **示例**：用于 PDF 旋转任务的 `scripts/rotate_pdf.py`
- **优点**：节省 token、具有确定性，且无需加载到上下文即可执行
- **注意**：agent 仍可能需要读取脚本，以便打补丁或按环境做调整

##### 参考文档（`references/`）

用于按需加载到上下文中，为 agent 的处理过程和思考提供信息的文档与参考资料。

- **何时包含**：当存在 agent 在工作时应查阅的文档时
- **示例**：用于财务模式定义的 `references/finance.md`、用于公司 NDA 模板的 `references/mnda.md`、用于公司政策的 `references/policies.md`、用于 API 规范的 `references/api_docs.md`
- **使用场景**：数据库模式定义、API 文档、领域知识、公司政策、详细的工作流指南
- **优点**：让 SKILL.md 保持精简，只在 agent 判断需要时才加载
- **最佳实践**：如果文件很大（超过 1 万词），在 SKILL.md 中给出 grep 搜索模式
- **避免重复**：信息应只存在于 SKILL.md 或参考文件中，而不是两者都放。详细信息优先放在参考文件里，除非它确实是技能的核心——这样既能让 SKILL.md 保持精简，又能让信息可被发现而不占用上下文窗口。SKILL.md 中只保留必要的程序性指令和工作流指导；把详细的参考资料、模式定义和示例移到参考文件中。

##### 素材（`assets/`）

不打算加载到上下文中，而是在 agent 产出的输出中使用的文件。

- **何时包含**：当技能需要用于最终输出的文件时
- **示例**：用于品牌素材的 `assets/logo.png`、用于 PowerPoint 模板的 `assets/slides.pptx`、用于 HTML/React 脚手架的 `assets/frontend-template/`、用于字体的 `assets/font.ttf`
- **使用场景**：会被复制或修改的模板、图片、图标、脚手架代码、字体、示例文档
- **优点**：把输出资源与文档分开，让 agent 无需加载即可使用这些文件

#### 技能中不应包含的内容

技能只应包含直接支撑其功能的必要文件。不要创建多余的文档或辅助文件，包括：

- README.md
- INSTALLATION_GUIDE.md
- QUICK_REFERENCE.md
- CHANGELOG.md
- 等等

技能只应包含 AI agent 完成手头工作所需的信息。它不应包含关于创建过程的辅助上下文、安装与测试流程、面向用户的文档等。额外创建文档文件只会增加杂乱和困惑。

### 渐进式披露设计原则

技能采用三级加载体系来高效管理上下文：

1. **元数据（name + description）** —— 始终在上下文中（约 100 词）
2. **SKILL.md 正文** —— 技能触发时加载（少于 5000 词）
3. **捆绑资源** —— 由 agent 按需加载（不设上限，因为脚本可以在不读入上下文窗口的情况下执行）

#### 渐进式披露模式

把 SKILL.md 正文控制在要点范围内，并保持在 500 行以内，以尽量减少上下文膨胀。接近该上限时，把内容拆分到独立文件中。拆分内容到其他文件时，务必在 SKILL.md 中引用它们并清楚说明何时阅读，以确保技能的读者知道这些文件存在以及何时使用。

**关键原则：** 当技能支持多种变体、框架或选项时，SKILL.md 中只保留核心工作流和选择指导。把变体特有的细节（模式、示例、配置）移到单独的参考文件中。

**模式 1：带参考文件的高层指南**

```markdown
# PDF Processing

## Quick start

Extract text with pdfplumber:
[code example]

## Advanced features

- **Form filling**: See [FORMS.md](FORMS.md) for complete guide
- **API reference**: See [REFERENCE.md](REFERENCE.md) for all methods
- **Examples**: See [EXAMPLES.md](EXAMPLES.md) for common patterns
```

agent 只在需要时才加载 FORMS.md、REFERENCE.md 或 EXAMPLES.md。

**模式 2：按领域组织内容**

对于涵盖多个领域的技能，按领域组织内容，避免加载无关上下文：

```
bigquery-skill/
├── SKILL.md（总览与导航）
└── reference/
    ├── finance.md（收入、计费指标）
    ├── sales.md（商机、销售漏斗）
    ├── product.md（API 用法、功能）
    └── marketing.md（营销活动、归因）
```

当用户询问销售指标时，agent 只读取 sales.md。

同样地，对于支持多种框架或变体的技能，按变体组织内容：

```
cloud-deploy/
├── SKILL.md（工作流 + 提供商选择）
└── references/
    ├── aws.md（AWS 部署模式）
    ├── gcp.md（GCP 部署模式）
    └── azure.md（Azure 部署模式）
```

当用户选择 AWS 时，agent 只读取 aws.md。

**模式 3：条件式细节**

展示基础内容，并链接到进阶内容：

```markdown
# DOCX Processing

## Creating documents

Use docx-js for new documents. See [DOCX-JS.md](DOCX-JS.md).

## Editing documents

For simple edits, modify the XML directly.

**For tracked changes**: See [REDLINING.md](REDLINING.md)
**For OOXML details**: See [OOXML.md](OOXML.md)
```

agent 只在用户需要这些功能时才读取 REDLINING.md 或 OOXML.md。

**重要准则：**

- **避免深层嵌套引用** —— 参考文件距 SKILL.md 只应有一层。所有参考文件都应直接从 SKILL.md 链接。
- **为较长的参考文件建立结构** —— 对于超过 100 行的文件，在顶部加入目录，以便 agent 预览时能看到完整范围。

## 技能创建流程

技能创建包括以下步骤：

1. 用具体示例理解技能
2. 规划可复用的技能内容（脚本、参考文档、素材）
3. 手动创建技能目录
4. 编辑技能（实现资源并编写 SKILL.md）
5. 验证技能结构
6. 根据实际使用情况迭代

请按顺序执行这些步骤，只有确实不适用时才跳过。

### 技能命名

- 只使用小写字母、数字和连字符；把用户提供的标题规范为连字符格式（例如 "Plan Mode" -> `plan-mode`）。
- 生成名称时，名称应不超过 64 个字符（字母、数字、连字符）。
- 优先使用描述动作的简短、动词开头的短语。
- 当有助于清晰或触发时，以工具作为命名空间前缀（例如 `gh-address-comments`、`linear-address-issue`）。
- 技能文件夹的名称必须与技能名称完全一致。

### 步骤 1：用具体示例理解技能

只有当技能的使用方式已经清楚理解时，才跳过此步骤。即使在处理已有技能时，这一步仍然有价值。

要创建高效的技能，需要清楚理解技能将被如何使用的具体示例。这种理解可以来自用户直接提供的示例，也可以来自生成并通过用户反馈验证的示例。

例如，在构建图像编辑技能时，相关问题包括：

- "图像编辑技能应支持哪些功能？编辑、旋转，还是其他？"
- "你能举一些这个技能会被如何使用的例子吗？"
- "我能想象用户会提出类似'去掉这张图片的红眼'或'旋转这张图片'的要求。还有你设想的其他使用方式吗？"
- "用户说什么话时应触发这个技能？"

为避免让用户不堪重负，不要在单条消息中问太多问题。先问最重要的问题，再根据需要追问以获得更好的效果。

当你能清楚把握技能应支持的功能时，本步骤即可结束。

### 步骤 2：规划可复用的技能内容

要把具体示例转化为高效的技能，请对每个示例进行分析：

1. 考虑如何从零开始实现该示例
2. 找出在反复执行这些工作流时会有用的脚本、参考文档和素材

示例：构建一个 `pdf-editor` 技能来处理"帮我旋转这个 PDF"这类请求时，分析表明：

1. 旋转 PDF 每次都需要重写相同的代码
2. 在技能中存放一个 `scripts/rotate_pdf.py` 脚本会很有用

示例：为"帮我做一个待办事项应用"或"帮我做一个记录步数的仪表盘"这类请求设计 `frontend-webapp-builder` 技能时，分析表明：

1. 编写前端 Web 应用每次都需要相同的 HTML/React 脚手架
2. 在技能中存放一个包含脚手架 HTML/React 项目文件的 `assets/hello-world/` 模板会很有用

示例：构建一个 `big-query` 技能来处理"今天有多少用户登录了？"这类请求时，分析表明：

1. 查询 BigQuery 每次都需要重新了解表结构和表间关系
2. 在技能中存放一个记录表结构的 `references/schema.md` 文件会很有用

为了确定技能的内容，请分析每个具体示例，列出要包含的可复用资源：脚本、参考文档和素材。

### 步骤 3：创建技能目录

此时应实际创建技能。

只有正在开发的技能已经存在时，才跳过此步骤。那种情况下，直接继续编辑和验证。

在 Chagent 配置的工作区下创建用户安装的技能：`<workspace>/skills/<skill-name>/`。如果 Chagent 被配置为使用非默认工作区，请把 `WORKSPACE` 设为该路径。

```bash
WORKSPACE="$HOME/.chagent/workspace"
mkdir -p "$WORKSPACE/skills/my-skill"
cat > "$WORKSPACE/skills/my-skill/SKILL.md" <<'EOF'
---
name: my-skill
description: Describe what this skill does and when Chagent should use it.
---

# My Skill

Describe the workflow the agent should follow.
EOF
```

对于随本仓库发布的技能，请创建在：

```text
workspace/skills/<skill-name>/
```

可选的资源目录：

- `scripts/` 用于可重复或脆弱的可执行操作
- `references/` 用于仅在需要时才加载的详细文档
- `assets/` 用于输出中使用的模板或文件

只创建技能真正需要的目录。创建目录后，按需定制 `SKILL.md` 并添加资源。除非辅助脚本已存在于当前仓库或技能包中，否则不要引用它们。

### 步骤 4：编辑技能

编辑（新生成或已有的）技能时，请记住该技能是供另一个 agent 实例使用的。应包含对 agent 有益且不显然的信息。思考哪些程序性知识、领域特有细节或可复用素材能帮助另一个 agent 实例更有效地执行这些任务。

#### 按需使用参考文件

为不应放在 `SKILL.md` 中的详细指导创建参考文件。只有当参考文件确实存在于技能中时，才链接它。

#### 从可复用的技能内容开始

开始实现时，先从上面确定的可复用资源入手：`scripts/`、`references/` 和 `assets/` 文件。注意这一步可能需要用户输入。例如，实现 `brand-guidelines` 技能时，用户可能需要提供品牌素材或模板放到 `assets/` 中，或提供文档放到 `references/` 中。

新增的脚本必须实际运行测试，以确保没有 bug 且输出符合预期。如果有很多相似的脚本，只需测试有代表性的样本，在保证信心的同时兼顾完成时间。

如存在未使用的占位文件，请删除它们。只创建真正需要的资源目录。

#### 更新 SKILL.md

**写作准则：** 始终使用祈使/不定式形式。

##### Frontmatter（前置元数据）

用 `name` 和 `description` 编写 YAML frontmatter：

- `name`：技能名称
- `description`：这是技能的主要触发机制，能帮助 agent 理解何时使用该技能。
  - 同时说明技能做什么，以及使用它的具体触发条件/场景。
  - 在这里包含所有“何时使用”的信息——不要放在正文中。正文只在触发后加载，因此正文里的“何时使用本技能”章节对 agent 没有帮助。
  - `docx` 技能的 description 示例："全面的文档创建、编辑和分析，支持修订痕迹、批注、格式保留和文本提取。当 agent 需要处理专业文档（.docx 文件）时使用：(1) 创建新文档，(2) 修改或编辑内容，(3) 处理修订痕迹，(4) 添加批注，或任何其他文档任务"

不要在 YAML frontmatter 中包含任何其他字段。

##### 正文

编写使用该技能及其捆绑资源的指令。

### 步骤 5：验证技能

在认为技能完成之前：

1. 确认技能目录中存在 `SKILL.md`。
2. 确认 YAML frontmatter 只包含 `name` 和 `description`。
3. 确认技能名称只使用小写字母、数字和连字符。
4. 确认所有被引用的文件确实存在。
5. 确认可选的 `scripts/`、`references/` 或 `assets/` 目录要么被技能使用，要么不存在。
6. 用有代表性的真实任务测试任何脚本或程序性指令。

如果 Chagent 将来记录了打包或验证命令，请使用该命令，而不要假设存在辅助脚本。

### 步骤 6：迭代

测试技能后，用户可能会要求改进。这通常发生在刚使用完技能、对技能表现记忆犹新的时候。

**迭代流程：**

1. 在真实任务中使用技能
2. 注意卡顿或低效之处
3. 确定应如何更新 SKILL.md 或捆绑资源
4. 实施修改并再次测试
